- (direction) Use the existing docs/ proposal discovery documents and ADRs as foundational requirements and constraints.
- (technique) started Question Storming
- (question) What questions must the project structure answer before it can be trusted in production, and what does production trust mean for thcode?
- (insight) The user is starting from a blank architectural slate and does not yet have production-structure questions.
- (insight) Primary concern: model compatibility and reliability for structured local tool calls and AI for Thai service invocation, including end-to-end performance.
- (idea) Provide a compact visible log of every model-proposed tool call, integrated with Manual permission review so the user can inspect the action before allowing it.
- (idea) Each tool-call approval entry leads with a brief plain-language description of what the tool is and what it will do, avoiding overwhelming users with raw code or terminal logs.
- (question) Should information sent to a called tool or AI for Thai service appear in the plain-language approval description?
- (idea) Coach spark: use a short approval summary with expandable transfer details for exact arguments, destination, selected data, and side effects.
- (idea) For executable local actions, the approval view shows the exact command the agent proposes to run; reading that command is the basis for approve or deny.
- (question) Would displaying the API endpoint be the right equivalent of showing an exact shell command for AI for Thai service calls?
- (idea) Coach spark: preview an AI service call as an HTTP request summary containing method, verified endpoint, service name, and a safe summary of the payload.
- (decision) For AI for Thai approval, show a safe HTTP request preview with method, verified endpoint, service, selected payload summary, and purpose; never expose credentials.
- (idea) Report specific remote-service failures to the user, distinguishing conditions such as AI for Thai being down, unreachable, or returning another identifiable error.
- (decision) thcode classifies remote-service failures from network evidence; the model receives the classified result and explains it clearly to the user.
- (decision) Users can inspect the deterministic error category and sanitized raw evidence alongside the model-generated explanation.
- (idea) Record duration and token usage for performance analysis, while preserving the documented distinction between Active Context Utilization and Cumulative Token Usage.
- (decision) Use one prompt round as the primary user-facing performance unit, recording its total end-to-end duration.
- (decision) Keep subsystem timing diagnostics available to developers while ordinary users see only the total duration for each prompt round.
- (technique) started Constraint Mapping
- (insight) Candidate hard constraints are AI for Thai service behavior, SCB X/Typhoon API credentials and access, and the selected model capabilities and behavior.
- (insight) thcode cannot guarantee output quality from external models or AI for Thai services; even an excellent harness can perform poorly when an upstream dependency performs poorly.
- (idea) thcode should provide a consistent user experience aligned with user intent despite variable model quality, covering the harness, structured tool calling, and a correct polished TUI.
- (decision) thcode owns the TUI and reliable tool-execution harness; model output quality remains the model provider’s responsibility, and the harness should continue supporting valid tool calls even when the reasoning quality is poor.
- (idea) Model-proposed or deterministically detected dangerous tool calls are visibly marked as dangerous and require the user to approve or deny them.
- (decision) Hard refusal should protect the host OS and out-of-workspace resources, such as destructive access to System32, while preserving substantial user freedom and avoiding unnecessary restrictions.
- (insight) Existing docs define Permission Profiles as operating within declared workspace, command, network, service, and quota boundaries; Full Access does not remove those boundaries, and sensitive transfer requires a separate override. The boundary-expansion workflow remains unspecified.
- (decision) Explicitly expanded workspace, command, or network boundaries should be saved and remain available across later thcode activations.
- (direction) Before further prompts, cross-check all docs/ decisions; do not ask the user to re-decide accepted requirements, and focus brainstorming only on unresolved architecture gaps or contradictions.
- (idea) Treat model-provider adapters, slash commands, and AI for Thai service integrations as extension points because new implementations will be added over time.
- (decision) Adding a provider, slash command, or AI for Thai service must not require changes to UI components or modifications to existing provider and service implementations.
- (idea) Extension developers configure their provider, command, or service metadata themselves; the TUI uses reusable generic components to render registered extensions without extension-specific UI code.
- (idea) At minimum, model extensions declare the model name, provider, and context-window size; the complete accepted provider-adapter metadata contract remains defined by ADR 0004.
- (technique) started Backcasting
- (idea) Store extension configuration files in a designated folder; thcode reads them through discovery and displays each extension correctly using reusable UI.
- (decision) End users can add provider configurations after installation, including local or private OpenAI-compatible endpoints such as Ollama and vLLM, without rebuilding thcode.
- (decision) User-created provider configuration is declarative and limited to endpoint and model configuration; it cannot execute custom adapter code.
- (decision) When a user configures a model, thcode performs a live API health check before showing the model as available.
- (decision) A configured provider requires only an API health check; thcode does not run a tool-calling compatibility test as part of provider availability.
- (decision) End users can configure custom specialist AI services, such as private OCR or speech-to-text endpoints, in addition to reasoning-model providers.
- (idea) Coach spark: use named protocol profiles—built-in OpenAI-compatible and Anthropic profiles for reasoning models, plus declarative HTTP request/response mappings for specialist AI services; configurations select a profile and provide endpoint-specific field mappings without executable code.
- (decision) Adopt named protocol profiles: built-in OpenAI-compatible and Anthropic profiles for reasoning providers, declarative HTTP request/response mappings for specialist services, and reviewed built-in adapters for unsupported protocols.
- (decision) Slash commands are implemented by thcode developers in reviewed TypeScript and shipped with the product; users cannot define slash commands through configuration.
- (technique) started Failure Analysis
- (decision) If a configured provider passes health check but fails its protocol during real use, thcode reports the specific error and requires the user to fix the configuration; it does not silently repair or reinterpret it.
- (decision) A provider that produces a protocol failure is marked unhealthy and cannot be reused until the user fixes its configuration and explicitly retests it.
- (decision) After a crash leaves a remote service request outcome uncertain, thcode does not retry automatically; the user must reprompt and deliberately send a new request.
- (idea) Restored history preserves the user prompt and records an explicit terminal marker such as Chat interrupted or Tool calling interrupted instead of inventing or retrying a response.
- (decision) After a crash, preserve every model response already received and append Chat interrupted at the point where execution stopped.
- (idea) Create prompt-level code-state checkpoints so the user can revert repository changes back to the state before the last prompt.
- (idea) Associate a reviewable diff with each prompt round, similar to GitHub or Codex change review, so users can inspect exactly what that round changed.
- (idea) Coach spark: record a private per-prompt change set with before hashes and exact agent patches, then revert through a conflict-aware reverse patch that removes only agent hunks and refuses automatic rollback when later user edits overlap.
- (decision) Use per-prompt before hashes and exact agent patches for rollback; automatically reverse only matching agent changes, and stop for manual conflict resolution when later edits overlap.
- (decision) For binary files changed or deleted by the agent, preserve the complete original file temporarily so prompt-level rollback can restore it.
- (decision) Retain prompt rollback checkpoints for five subsequent prompts by default, with configurable retention in settings, then delete expired checkpoint data.
- (decision) Convergence verdict: make the provider and specialist-service extension platform the architectural foundation because without usable model and service connectivity there is no functional agentic CLI; safety, UX, observability, and recovery build around that core.
- (insight) Final synthesis: the provider and specialist-service platform is the production architecture foundation. Declarative configuration, protocol profiles, generic UI discovery, API health checks, and unhealthy-state handling form one extension lifecycle; approval previews, error evidence, and performance metrics make that lifecycle observable and trustworthy. Prompt rollback and crash recovery remain supporting infrastructure around this core.
