## Intent

**Problem:** A Specialist transfer requires a `PreparedPayloadManifest` binding the exact payload-byte digest + canonical manifest digest + recipient + verified endpoint + purpose + call count + scope + expiry + retention/deletion classification, and an INDEPENDENT fresh consent per exact transfer. Full Access, local approval, cache reuse, or prior consent must never substitute for a fresh exact consent decision (AD-17). Story 2.6 already provides the generic contracts (`PreparedPayloadManifest`, `TransferConsent`, `evaluateTransferConsent`, `revalidateTransferConsent`) — but there is no Specialist-specific preparation that builds the manifest from the resolved/minimized artifacts (4.6/4.7) + the effective configuration (4.4) + the routing proposal (4.5), maps the registry entry's retention/privacy/classification to the manifest fields (fail-closed `unknown` retention → blocked per AD-26.1), exposes a secret-free `ConsentReference` for Evidence/dialog, or renders the `transfer-consent-dialog` surface (recipient, verified HTTPS endpoint, purpose, method, safe payload summary, source identity, classification, retention/deletion status, side effects, manifest digest, payload digest, ConsentReference; credentials/secrets never appear; initial focus `consent-review`/`consent-cancel`, never Consent).

**Approach:** Add a Specialist consent module under `cli/src/core/specialists/consent/` that SPECIALIZES the existing `cli/src/core/permissions/transferConsent.ts` contracts — it does NOT duplicate authority semantics. `buildSpecialistPreparedPayloadManifest` maps a routing proposal + prepared/minimized artifacts + `SpecialistEffectiveConfiguration` + registry entry into a `PreparedPayloadManifest` (sources from artifacts, recipient from config, classification from privacy, transformation from minimization transforms, retention from the entry's `retentionClassification` via a conservative `resolveRetentionHandling` that yields `unknown` → blocked unless explicitly verified no-retention/deletion-confirmed, purpose from the routing rationale, payload-byte digest over the ordered exact prepared bytes). `requestSpecialistTransferConsent` wraps `evaluateTransferConsent` with the Specialist activation/authority/policy context; `revalidateSpecialistTransferConsent` rechecks immediately before transport. `ConsentReference` is a secret-free handle to a granted consent (consentId + both digests + recipient + grantedAt + expiresAt) for Evidence/dialog. `buildConsentDialogSummary` renders the `transfer-consent-dialog` surface data — secret-free, with a safe payload summary and initial focus `consent-review`/`consent-cancel`. The manifest + consent bind BOTH the canonical manifest digest AND the exact payload-byte digest; any change after consent marks it `mismatch`/`stale` and blocks sending (revalidation fails closed).

## Boundaries & Constraints

**Always:**
- Reuse `cli/src/core/permissions/transferConsent.ts` — do NOT re-implement `PreparedPayloadManifest`, `TransferConsent`, `evaluateTransferConsent`, `revalidateTransferConsent`, `computeManifestDigest`, `assessPreparedPayloadSafety`, `detectUnsafePreparedContent`. The Specialist module only maps inputs into these contracts and projects results.
- The manifest binds BOTH the canonical `manifestDigest` AND the exact `payloadByteDigest`; both are recomputed/revalidated immediately before transport (AC #3 of Story 2.6). Any changed field → `manifest-digest-mismatch`; any changed payload bytes → `payload-byte-digest-mismatch`; either blocks sending.
- Consent is INDEPENDENT per exact transfer: Full Access, local approval, cache reuse, and prior consent NEVER substitute for fresh consent (AD-17). The PEP/consent gate returns `ask`/`deny` independently of Work Mode, Profile, or Full Access.
- Retention mapping is conservative (AD-26.1, PR-2): `resolveRetentionHandling(entry)` yields `upstream-no-retention-verified` only when the entry's `retentionClassification.policy` explicitly verifies no upstream retention AND `providerDeletionSupported` is consistent; `deletion-confirmed`/`deletion-not-required` only when the contract explicitly declares it; otherwise `unknown`. `unknown` retention → `evaluateTransferConsent` fails closed (`retention-unknown`) → transfer BLOCKED, never assumed safe.
- `unresolved` classification (an unresolved local path or un-classified payload) → `classification-unresolved` → blocked.
- Credentials and raw secrets NEVER appear in the manifest, the consent, the `ConsentReference`, or the dialog summary. Sources carry identity + hash + mediaType + size only (never raw bytes).
- The `payloadByteDigest` is computed over the ordered exact prepared bytes/text of the minimized artifacts (the bytes that would actually be transported) — deterministic, recomputed before transport.
- The dialog surface initial focus is `consent-review` or `consent-cancel` — NEVER `Consent` (auto-grant). The dialog never displays credentials/raw secrets; the payload summary is safe (sizes + media types + source identities + hashes, not contents).
- Injectable clock for `grantedAt`/`expiresAt`; no `new Date()`/`Date.now()`/`Math.random()` in pure logic (the existing `randomId()` via `randomUUID()` is used for `consentId` — that is acceptable since it is in the existing module).

**Block If:** (none unattended — deterministic from the routing proposal, the prepared artifacts, the effective configuration, the registry entry, and the activation/authority/policy context)

**Never:**
- Never duplicate the Story 2.6 consent authority semantics.
- Never substitute Full Access/local approval/cache/prior consent for a fresh exact consent.
- Never map `unknown` retention to a safe value; never assume deletion is supported when the contract doesn't declare it.
- Never include raw bytes/secrets/credentials in the manifest, consent, ConsentReference, or dialog.
- Never auto-grant consent (initial focus is never `Consent`).

## Design Notes

Reuse `cli/src/core/permissions/transferConsent.ts` EXACTLY — import `PreparedPayloadManifest`, `TransferConsent`, `buildPreparedPayloadManifest`, `computeManifestDigest`, `evaluateTransferConsent`, `revalidateTransferConsent`, `assessPreparedPayloadSafety`, `detectUnsafePreparedContent`, `SelectedSource`, `PayloadClassification`, `TransformationPolicy`, `Recipient`, `RetentionHandling`, `ConsentEvaluationResult`, `PREPARED_PAYLOAD_MANIFEST_VERSION`. Do NOT re-implement. The Specialist module is a mapping + projection layer. `SelectedSource.identity` = the artifact's `sourceIdentity.canonicalPath` (or displayPath — prefer canonicalPath; it's not the raw secret, it's a workspace path, which is acceptable as identity per the existing contract: "path/hash/metadata, never the raw bytes"). `sourceHash` = the artifact's `contentHash` (post-minimization). `PayloadClassification` mapping: artifact `privacyClassification` `public`→`public`, `internal`→`internal`, `secret`→ should never reach here (4.6 blocks secret) but if it does → `unresolved` (blocked). `sensitive` is not in the artifact's PrivacyClassification (`public`|`internal`|`secret`) — map `internal` to `internal` and `public` to `public`; if the registry entry's `privacyClassification.requiresConsent` is true, the consent gate already enforces it. The manifest `classification` field uses `PayloadClassification` (`public`|`internal`|`sensitive`|`unresolved`): map `internal`→`internal`, `public`→`public`, and when `entry.privacyClassification.requiresConsent` or dataClasses include sensitive classes → `sensitive`. `resolveRetentionHandling` keyword matching: policy string containing "no-retention"/"none"/"zero-retention"/"retention:none" → `upstream-no-retention-verified` (only if `providerDeletionSupported` is consistent or policy explicitly says no retention needed); "deletion-confirmed" → `deletion-confirmed`; "deletion-not-required"/"not-required" → `deletion-not-required`; else `unknown`. Be conservative — when in doubt, `unknown` (blocked). `computePayloadByteDigest`: for each artifact in order, frame as `<mediaType>:<contentHash>:<len>:<content bytes>` and hash the concatenation (the framing ensures order + identity matters; an empty payload still hashes the framing). Use `createHash('sha256')`. The app accessor: `authorityRevision: a.revision` (activation revision, matching existing app.ts convention), `policyVersion: 1` (existing convention), `now: this.clock()`. Sanitizer: reuse `sanitizer.sanitize(text, contentClass)` for text payloads; for binary payloads, the sanitizer operates on text so pass an empty/safe string and rely on `detectUnsafePreparedContent` for path/secret markers — keep it simple and consistent with how Story 2.6 expects. Inject `clock`; no `new Date()`/`Date.now()`/`Math.random()` in the new pure functions. Tests: vitest, build `PreparedArtifact` fixtures directly, no real network/fs.
